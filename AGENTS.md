## What this is

A local Rust HTTPS MITM proxy for the `claude` CLI:

1. **Caches Google OAuth tokens** so `oauth2.googleapis.com/token` round-trips don't happen on every invocation.
2. **Short-circuits Vertex AI heat-up requests** (`max_tokens: 1`, single `"."` user message) so they never burn upstream tokens.
3. **Deduplicates byte-identical concurrent requests** so a duplicate POST results in one upstream call, with both clients receiving the buffered response.
4. **Auto-recovers from expired credentials** — on `invalid_grant` from Google OAuth, opens a browser, runs the consent flow, writes a fresh ADC, and returns a valid token to the client transparently.
5. **Map Local** — for configured `[[map_local]]` rules (URL pattern + method), returns a fixed inline body or local file instead of forwarding upstream. Lets users silence telemetry endpoints, neuter update checks, and replay canned fixtures without burning real API tokens.
6. **Gemini providers** — serves the native Gemini API (`/v1beta/models…`) for opencode's `@ai-sdk/google`, routing each model to the `gemini-cli` or `antigravity` Cloud Code Assist upstream by a **provider prefix** on the model name (`gemini-cli/<model>`, `antigravity/<model>`), with browser `login` for each. Works both as a plain-HTTP origin and via MITM of `generativelanguage.googleapis.com`. Credentials live in `~/.config/claude-proxy/auths/` and are also read from `~/.cli-proxy-api/` (CLIProxyAPI-compatible). See [wiki/gemini-providers.md](wiki/gemini-providers.md).
7. **Anthropic Messages API** — serves `POST /v1/messages` (+ `/v1/messages/count_tokens`) for any Anthropic-API client (Claude Code via `ANTHROPIC_BASE_URL`, the Anthropic SDK), driving the **same** `gemini-cli`/`antigravity` upstreams via the same provider prefix on the body's `model`. It does this by translating Anthropic↔native-Gemini and reusing the Gemini envelope/upstream/SSE layer. Works as a plain-HTTP origin, and via MITM of `api.anthropic.com` **gated on the provider prefix** — unprefixed models fall through to the real Anthropic API so the normal `claude` CLI is untouched. See [wiki/gemini-providers.md](wiki/gemini-providers.md).
8. **Claude subscription passthrough** — serves `POST /v1/messages` (+ `/count_tokens`) against the **real** Anthropic API using the Claude Code OAuth credential from the **macOS Keychain**, so any Anthropic-API client can drive the user's Claude subscription without an `sk-ant-api…` billing key. No format translation (Anthropic in, Anthropic out); the work is credential refresh plus a **request disguise** — Anthropic only honors an OAuth credential when the request looks like Claude Code. Origin mode serves prefixed *and* (by default) plain model names; MITM of `api.anthropic.com` serves **only** the explicit `claude-oauth/` prefix, so the real `claude` CLI is never hijacked. See [wiki/claude-oauth.md](wiki/claude-oauth.md).
9. **Gemini Enterprise seat (`aicode/`)** — serves a Gemini Enterprise /
   AntiGravity team coding seat over the `businessaicode` API, as a fourth
   provider prefix on both the `/v1beta` and `/v1/messages` surfaces. Different
   upstream from the `antigravity` provider (regional
   `businessaicode.<loc>.rep.googleapis.com` host, a
   `/projects/<p>/locations/<l>:` path, a **flat field-allowlisted** body whose
   model selector is `aicode.experience`), driven by a *borrowed* `gemini-cli`
   credential. Project/location/tier are discovered from `:fetchLicenses` with
   `[aicode]` overriding. See [wiki/gemini-providers.md](wiki/gemini-providers.md).
10. **OpenAI Chat Completions aggregator** — serves `POST /v1/chat/completions` (origin mode only: `OPENAI_BASE_URL=http://127.0.0.1:7777`) and fans it out to multiple OpenAI-compatible upstreams configured under `[[openai]]` (`name` + `base_url` + optional `api_key`/`headers`). Routing splits the model on the **first** `/`: the head selects the `[[openai]]` provider, the remainder is forwarded verbatim as the upstream `model` (`opengateway/minimax/minimax-m3` → provider `opengateway`, upstream model `minimax/minimax-m3`). **No format translation** — OpenAI in, OpenAI out, a near-pure pipe (rewrite `model`, forward, stream the response back byte-exact). No MITM, no `/v1/models`. Lives in [src/openai/mod.rs](src/openai/mod.rs).

Everything else passes through to `reqwest`, optionally chained via `HTTPS_PROXY` / `config.toml` `upstream_proxy` (e.g. Proxyman, mitmproxy at `localhost:9090`).

## Key invariants — do not break

- **`PrimaryGuard` is RAII.** The primary OAuth fetcher owns a `PrimaryGuard` whose `Drop` impl removes the in-flight entry from `TOKEN_PROMISES`. This is what prevents secondary waiters from hanging forever if the primary's task is cancelled (e.g., client disconnect). Resolve via `guard.resolve(token)` for normal completion; never call `mem::forget` on it; never re-introduce the old `resolve_token_promise` free function.
- **`RequestPrimaryGuard` is RAII (same pattern).** Mirrors `PrimaryGuard` for the generic request-dedup map (`REQUEST_PROMISES`). Always resolve via `guard.resolve(Some(buf))` on 2xx or `guard.resolve(None)` on non-2xx / upstream error so secondaries fall through to native fetch. The `Err` arm of the upstream send must resolve too — leaking a guard there strands secondaries until Drop fires. On the **routed Anthropic path** the guard is resolved by `proxy::record_for_dedup` instead: buffered responses are collected and resolved inline; streams are wrapped in `RecordingBody`, which resolves at EOF. `RecordingBody` deliberately does **not** override `is_end_stream`/`size_hint` — the defaults are what keep hyper polling to `Ready(None)`, and that final poll is the only thing that resolves the promise. On client disconnect the body is dropped with the guard still held, so the same `Drop` eviction applies.
- **`ReauthGuard` is RAII and lives inside a `tokio::spawn`-ed task.** The OAuth browser flow must outlive the request handler that triggered it — clients commonly time out during the 5-minute browser window, and the next retry depends on finding the in-progress flow via `REAUTH_PROMISE`. Keep `run_oauth_flow()` spawned, not inline. See [wiki/auto-reauth.md](wiki/auto-reauth.md).
- **The token-exchange POST in `reauth.rs` uses a `no_proxy()` `reqwest::Client`.** The proxy's main client may chain through `HTTPS_PROXY` (which is us). A proxied exchange would loop back through the very interceptor that triggered re-auth. Don't share the proxy's `reqwest::Client` with `reauth.rs`. **Same rule applies to `login.rs` (all calls), `gemini::creds` token refresh, and `claude_oauth::creds` token refresh** — `login` runs in the user's shell where `HTTPS_PROXY` points at us, so a default client would self-loop. The Gemini *upstream* generate/stream call deliberately reuses the proxy's main client so it benefits from `upstream_proxy` chaining (Proxyman); that's not a loop because cloudcode-pa ≠ us. **The OpenAI aggregator's and Claude-OAuth surface's upstream POSTs reuse the proxy's main client for the same reason** (the configured `base_url` / `api.anthropic.com` ≠ us), so don't switch them to a `no_proxy()` client.
- **The Claude-OAuth credential write-back must merge, never replace.** The Keychain item (`Claude Code-credentials`) also holds `mcpOAuth`, `pluginSecrets`, and `organizationUuid`, all owned by the real `claude` CLI, plus unknown keys inside `claudeAiOauth` itself. `claude_oauth::creds::persist` re-reads the item and replaces only `accessToken`/`refreshToken`/`expiresAt`; a whole-object write would silently destroy the user's MCP logins. Write-back is on by default deliberately — Anthropic rotates the refresh token, so keeping ours private would eventually invalidate the real Claude Code login.
- **The Claude-OAuth disguise's three tiers must stay separate** ([src/claude_oauth/disguise.rs](src/claude_oauth/disguise.rs)): *auth-critical* (identity `system` block, `oauth-2025-04-20`) and *cosmetic* (billing `system[0]`, user-agent, `x-stainless-*`, `metadata.user_id`, `diagnostics`) are injected unconditionally; *semantic* fields (`context_management`, `output_config`, `thinking`, sampling params) are forwarded but **never invented**, because inventing them silently changes what the caller asked for. `[claude_oauth.inject]` is the deliberate escape hatch, and client values always win over it. Also: neither injected `system` block carries `cache_control` (it would consume one of the client's four breakpoints), and `anthropic-beta` is a **fixed configured list, not a union with the client's** — Anthropic 400s on any beta it doesn't recognize, so forwarding a caller's list turns one stray identifier into a total failure.
- **Pipeline order: Map Local → Gemini → Anthropic → Claude-OAuth → OAuth → Vertex heat-up → dedup → upstream forward.** Map Local sits at the very top so a mapped URL fully bypasses everything else (a user mapping the OAuth endpoint to a fixture wants the fixture, not the disk-cached token). Gemini then Anthropic routing come next so a `/v1beta` or `/v1/messages` request is fully served (translated to the provider upstream) and never touches the OAuth-token cache or the Vertex heat-up check, which are specific to the `claude` CLI's traffic. **Dedup is the one exception: the routed Anthropic path registers in `REQUEST_PROMISES` itself** (both transports), because the early return jumps over the shared dedup block below and Claude Code fires byte-identical concurrent `/v1/messages` requests for session-title generation — one provider generation per duplicate otherwise. The two uses share the map and key safely: routability is a pure function of the body, so a routed and a forwarded request can never collide. Heat-ups must short-circuit before the dedup map is touched, otherwise a heat-up-shaped body would inflate the in-flight set with synthetic-response candidates. Keep the order in [src/proxy.rs::handle_intercepted_request](src/proxy.rs). **The Claude-OAuth surface registers in `REQUEST_PROMISES` the same way, for the same reason, on both transports.** The plain-HTTP branch of `handle_request` runs Map Local → Gemini → (Claude-OAuth → Anthropic) → OpenAI (origin mode); non-mapped, non-Gemini, non-Anthropic, non-OpenAI plain HTTP still 500s. Note the origin-branch order **inside** the `/v1/messages` block: Claude-OAuth is checked **before** `gemini::anthropic::try_handle`, because that handler *serves* every `/v1/messages` POST (404-ing an unroutable model) rather than declining, and would otherwise shadow the Claude-OAuth surface entirely. `claude_oauth::routes` never claims a model the Gemini-Anthropic surface would serve (prefixed or `[anthropic_model_map]`-redirected), so existing traffic keeps its destination. Compression is deliberately skipped on the Claude-OAuth path — the upstream *is* Anthropic, so the body must arrive as the client wrote it. The one rewrite that *does* apply there is `claude_oauth::heal_transcript` (both transports, inside `try_handle` so no transport can forget it): the same two scrubs the unrouted fall-through runs, for the same reason — this surface's upstream is the real Anthropic API, so a transcript poisoned by a provider-backed turn 400s here identically. Removing blocks the API refuses isn't the same as mangling content the client meant to send. The OpenAI aggregator (`/v1/chat/completions`) is plain-HTTP/origin-only — it is **not** wired into the MITM branch at all (no `api.openai.com` interception), so there's no MITM safety gate to maintain for it. In the MITM branch, Gemini routing is gated on `host == generativelanguage.googleapis.com`, and **Anthropic routing is gated on `host == api.anthropic.com` AND the body's `model` being routable** (`anthropic::routed_provider`) — this is the safety crux: a request whose model is neither provider-prefixed nor explicitly listed in `[anthropic_model_map]` falls through to the normal upstream forward (the real Anthropic API), so the `claude` CLI is never hijacked. (Two narrow rewrites apply on that fall-through, both healing transcript poison left by the gemini→claude translation and both re-serializing only when a block was actually removed, so healthy traffic is forwarded byte-identical: `anthropic::scrub_empty_text_blocks` strips empty assistant `text` content blocks — an earlier streaming bug the real API rejects with `messages: text content blocks must be non-empty` — and `anthropic::scrub_unsigned_thinking_blocks` strips assistant `thinking` blocks whose `signature` is empty or missing, which is every thinking block we produce, since only Anthropic can mint a valid signature; the real API rejects those with ``Invalid `signature` in `thinking` block``. Both substring-pre-check before parsing via the shared `has_string_value` — `"text":""` for the text scrubber, `"type":"thinking"` for the thinking one, since the block we emit has no `signature` key at all and keying on `"signature":""` would miss it.) `[anthropic_model_map]` (`config.rs`, empty by default) is the one deliberate, narrow exception — an exact-match config that lets a specific real Anthropic model name (e.g. `claude-sonnet-5`) be redirected to a provider-prefixed target over **either** transport (this is the feature's actual purpose: redirecting the real `claude` CLI's MITM'd traffic); it does not weaken the gate for any model not explicitly listed. **The Claude-OAuth surface has the same safety crux and a stricter gate: over MITM it routes on the explicit `claude-oauth/` prefix only** (`claude_oauth::routes(..., allow_unprefixed: false)`), because an unprefixed model on `api.anthropic.com` is the real `claude` CLI using its own credential. `serve_unprefixed` (default true) applies to the plain-HTTP origin branch *only* — never widen it to MITM. See [wiki/gemini-providers.md](wiki/gemini-providers.md) and [wiki/claude-oauth.md](wiki/claude-oauth.md).
- **All handlers return `Response<ProxyBody>` (boxed body).** `ProxyBody = BoxBody<Bytes, std::io::Error>`. Buffered responses use `full_body(bytes)`; the interceptor helpers still return `Response<Full<Bytes>>` and are re-boxed at the call site with `box_full(...)`. The Gemini and Anthropic SSE paths are the true streams — both built on the one disconnect-safe `provider::stream_sse` pump (keep the `biased` `tokio::select!` on `tx.closed()`). Don't revert the handler signatures to `Full<Bytes>` — streaming depends on the boxed type.
- **Dedup cache key keeps the canonical `format!("{} {}\n{}", method, url, body_str)` layout** — two whitespace-separated fields, then the body — and is built only by `proxy::dedup_key`. Method + URL prevent unrelated empty-body GETs from false-deduping; body is the discriminator. The routing namespace rides **inside the URL field** as a `#mode=` fragment (`…/v1/messages#mode=routed-claude`) rather than adding a third field, so the layout is unchanged; a fragment can't occur in a real request target. The modes (`routed-gemini` / `routed-claude` / `forward`) come from a private `DedupMode` enum in [src/proxy.rs](src/proxy.rs) and keep an entry from one surface from being replayed to a request another would serve. That dimension is **defense in depth, not a live fix** — every mode is chosen by a pure function of the body, which is already in the key — but it stops that purity from being load-bearing. The layout is pinned by tests in [src/proxy.rs](src/proxy.rs); if you ever change it, update [wiki/request-dedup.md](wiki/request-dedup.md).
- **Cache key is the request body.** `~/.config/gcloud/application_default_credentials_access_token.json` stores the original `request_body` alongside the token; cache hits require an exact body match. If a caller's body varies between calls (e.g., JWT-bearer flows where `iat`/`exp` change), the cache will miss every time. If you need to support that case, change the key strategy — don't paper over it.
- **Upstream forwarding strips three headers**: `host`, `accept-encoding`, `content-length`. Keep that list in sync if you add header logic; messing with `accept-encoding` will silently break OAuth JSON parsing (we don't enable reqwest's `gzip` feature).
- **`danger_accept_invalid_certs(true)`** on the upstream `reqwest::Client` is intentional — it lets us chain through Proxyman/mitmproxy. Don't remove it.
- **Listening port defaults to `127.0.0.1:7777`** ([`proxy::DEFAULT_PORT`](src/proxy.rs)) but is configurable. Precedence: CLI `--port` > config `port` > `DEFAULT_PORT`, resolved by [`config::resolve_port`](src/config.rs). The daemon `start` loads config *before* binding so the config `port` feeds the bind (and reuses that config in the forked child); `restart` resolves the same way for its socket-release probe. Keep all three call sites (`main::run_foreground`, `daemon::start`, `daemon::restart`) going through `resolve_port` so precedence stays consistent.

## Build and test

```bash
cargo build              # debug
cargo build --release    # what users actually run
RUST_LOG=claude_proxy=debug,reqwest=debug,hyper=info target/release/claude-proxy
```

Unit tests exist for the pure helpers (compression, wildcard matching, OAuth callback parsing, the Anthropic scrub/translation guards, and the whole Claude-OAuth disguise + routing gate) — run `cargo test`. Everything transport-shaped is untested; validate changes by:
1. Building.
2. Running the proxy.
3. Running `claude` with `HTTPS_PROXY=http://127.0.0.1:7777` and `NODE_EXTRA_CA_CERTS=~/Library/Application\ Support/claude-proxy/ca.crt`.
4. Watching logs for the expected `Cache hit on disk for token` / `Intercepted Vertex AI heat-up request` lines on subsequent invocations.
5. For dedup: fire two byte-identical concurrent POSTs at the proxy (the `curl` pair in [wiki/request-dedup.md](wiki/request-dedup.md#validation)) and confirm the log shows one `We are the primary fetcher` plus one `Waiting on primary in-flight request` followed by `Received response from primary in-flight request`.
6. For the Claude-OAuth surface: the eight `curl` cases in [wiki/claude-oauth.md](wiki/claude-oauth.md#verification) — non-stream, stream, client-system-prompt survival, `count_tokens`, **both** MITM gate directions (unprefixed must come back `invalid x-api-key` from the real API; prefixed must be served by us despite the bogus key), dedup, and Gemini-not-stolen.

## Things to be careful about

- **rcgen is pinned to 0.11.** 0.14 has a different API (no `Certificate::from_params`, `from_ca_cert_pem`); reverting was deliberate. Don't bump it without rewriting [src/certs.rs](src/certs.rs).
- **rand is 0.10**, which uses `RngExt::sample_iter` (not the older `Rng::sample_iter`). Keep the `RngExt` import in [src/interceptors.rs](src/interceptors.rs).
- **`aicode` never writes to the credential file, and never reads `project_id` as a licence project.** It borrows a `gemini-cli` credential via `aicode::resolve_account` + `ensure_fresh`, deliberately **not** `creds::resolve_account` — that lazy-onboards a Code Assist project when `project_id` is empty, and *writes it back to the file*. Putting a Gemini Enterprise licence project into the field the `gemini-cli` provider reads would break plain `gemini-cli/*` requests in a way that outlives the process. The credential's `project_id` has exactly one legitimate use here: a candidate `x-goog-user-project` value for the `:fetchLicenses` metadata GET, which is a billing handle, not the licence.
- **`aicode`'s location *and project* are charset-validated on the value that came off the wire, not just the configured one.** The location lands in the authority (`businessaicode.<loc>.rep.googleapis.com`); the project lands in two URL path segments **and** in the `x-goog-user-project` header value, where a `/` addresses a different resource and a newline is a request-splitting shape. Both go through `aicode::valid_location` / `valid_project` (one shared charset, two names because the exposure differs), at config load *and* again after `:fetchLicenses` — the discovered value is the one nobody typed, which is the call site that matters.
- **Don't add features the proxy doesn't need.** This codebase is intentionally narrow — it intercepts a handful of endpoints, serves the Gemini + Anthropic APIs, and forwards the rest. Resist adding "while we're here" abstractions. The Gemini layer deliberately ports only the Gemini↔provider transform; the Anthropic layer adds **only** the Anthropic↔native-Gemini boundary and reuses everything downstream (it does **not** re-implement the dedicated `antigravity/claude` signature path — claude-on-antigravity rides the gemini envelope + `VALIDATED` toolConfig tweak + the antigravity tool-schema cleaner in `schema_clean.rs`, same as the `/v1beta` surface). **Gotcha:** for antigravity, tool schemas must be sent as `functionDeclarations[].parameters` (not `parametersJsonSchema`) and cleaned of unsupported JSON-Schema keywords — that step lives in CLIProxyAPI's *executor*, not its translator, so it's easy to miss; without it the Vertex Anthropic backend returns `tools.0.custom.input_schema: Field required`. Deferred items (`stop_sequences`, the dedicated `antigravity/claude` signature path, etc.) are listed in [wiki/gemini-providers.md](wiki/gemini-providers.md). (`max_tokens`→`maxOutputTokens` **is** mapped — the `-thinking` models need `max_tokens > thinking.budget_tokens`.)
- **The `GET /v1beta/models` listing is fetched live per provider** — gemini-cli via `cloudcode-pa …:retrieveUserQuota`, antigravity via `daily-cloudcode-pa …:fetchAvailableModels` — each using the same hardcoded client headers as the generate path. There is **no embedded and no remote catalog** (both removed); an optional `[settings] models_file` (`models.json` on disk) is the only fallback/enrichment source, used per-provider when its live fetch fails. The listing never gates routing (prefix-based). If you ever add a non-`.rs` runtime asset under `src/`, add it to [Cargo.toml](Cargo.toml)'s `include` list or `cargo publish` will exclude it.
- **README.md must use full GitHub URLs for `wiki/` links.** The `include` list in [Cargo.toml](Cargo.toml) ships `README.md` to crates.io but **not** the `wiki/` directory — relative links like `[wiki/auto-reauth.md](wiki/auto-reauth.md)` render as broken links on the crates.io page. Always link wiki pages from README.md as `https://github.com/aeroxy/claude-proxy/blob/master/wiki/<file>.md` — note the owner is `aeroxy` (matching `git remote`), not `aero`. Internal docs (AGENTS.md, CLAUDE.md, GEMINI.md, other wiki pages) can keep relative paths since they're never published to crates.io.

## Intentionally trusting

claude-proxy is a single-user MITM proxy on `127.0.0.1` that assumes a trusted local environment. Security findings whose threat model requires a *local* process/user the operator doesn't control are intentionally **not** fixed — the only realistic "attacker" is the operator themselves chaining another proxy downstream on purpose.

Concrete decisions in this class (all deliberate, don't re-flag or "harden"):
- OAuth `state` is generated and sent in the login auth URL but **not** validated on the callback (CSRF / code-injection on the loopback callback port). Declined 2026-05.
- `danger_accept_invalid_certs(true)` on the upstream client (to chain through Proxyman/mitmproxy).
- Inbound API keys (`x-goog-api-key`, Anthropic key) are ignored — real auth is the stored OAuth credential.
- Account email is logged to local logs across the Gemini/creds/login paths.

**Why:** trusted-local-network assumption; a local attacker already has the operator's privileges, so these guards add cost for no real benefit here.
